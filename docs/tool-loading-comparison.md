# 三种工具加载方案对比

## 方案概览

### 方案 A：传统完整工具定义
**描述**：每次请求携带所有 20+ 个工具的完整定义

### 方案 B：Tool-as-Skill（当前方案）
**描述**：只携带 1 个 useSkill 工具，所有工具作为 enum 参数

### 方案 C：延迟加载（新方案）
**描述**：系统提示词中只有文本描述，需要时才注入工具定义

## 详细对比

### Token 消耗对比

| 场景 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 普通对话（不用工具） | 2300 | 700 | 400 |
| 使用 1 个工具 | 2300 | 700 | 400 + 500 = 900 |
| 使用 3 个工具 | 2300 | 700 | 400 + 500×3 = 1900 |

**分析**：
- 方案 C 在不使用工具时最优（400 tokens）
- 方案 C 在使用 1 个工具时稍差（900 vs 700）
- 方案 C 在使用多个工具时最差（需要多次请求）

### 缓存命中率对比

| 方案 | 缓存命中条件 | 预期命中率 |
|------|-------------|-----------|
| 方案 A | 工具列表不变 | 中等（~60%） |
| 方案 B | useSkill 定义不变 | 高（~95%） |
| 方案 C | 系统提示词不变 | 极高（~99%） |

**分析**：
- 方案 A 会因为工具列表变化（联网开关等）导致缓存失效
- 方案 B 的 useSkill enum 变化时缓存失效
- 方案 C 系统提示词几乎永不变化

### 响应延迟对比

| 场景 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 不使用工具 | 1x | 1x | 1x |
| 使用工具 | 1x | 1x | 2x（两次请求） |

**分析**：
- 方案 C 需要两次 API 请求，增加延迟
- 但可以通过流式输出优化用户体验

### 实现复杂度对比

| 方面 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 代码复杂度 | 简单 | 中等 | 复杂 |
| 维护成本 | 低 | 中 | 高 |
| 扩展性 | 中 | 高 | 极高 |

## 适用场景分析

### 方案 A：传统完整工具定义
**适用于**：
- 工具数量少（< 10 个）
- 不关心 token 消耗
- 需要最简单的实现

**不适用于**：
- 工具数量多（> 20 个）
- 需要控制成本
- 使用本地小模型（上下文受限）

### 方案 B：Tool-as-Skill（推荐）
**适用于**：
- 工具数量多（20+ 个）
- 平衡 token 消耗和复杂度
- 大部分场景都会使用工具
- 需要稳定的缓存命中率

**不适用于**：
- 极致优化 token 消耗
- 大量不使用工具的对话

### 方案 C：延迟加载
**适用于**：
- 极致优化初始上下文
- 对话中很少使用工具
- 可以接受两次请求的延迟
- 需要最高的缓存命中率

**不适用于**：
- 对延迟敏感的场景
- 频繁使用多个工具
- 需要简单实现

## 实际成本分析

假设：
- GPT-4 输入成本：$0.03 / 1K tokens
- 每天对话 1000 次
- 50% 对话使用工具

### 方案 A 成本
```
不使用工具：500 × 2300 tokens = 1,150,000 tokens
使用工具：500 × 2300 tokens = 1,150,000 tokens
总计：2,300,000 tokens/天 = $69/天 = $2,070/月
```

### 方案 B 成本
```
不使用工具：500 × 700 tokens = 350,000 tokens
使用工具：500 × 700 tokens = 350,000 tokens
总计：700,000 tokens/天 = $21/天 = $630/月
```

### 方案 C 成本
```
不使用工具：500 × 400 tokens = 200,000 tokens
使用工具：500 × (400 + 500) tokens = 450,000 tokens
总计：650,000 tokens/天 = $19.5/天 = $585/月
```

**结论**：
- 方案 B 比方案 A 节省 **70%** ($1,440/月)
- 方案 C 比方案 B 再节省 **7%** ($45/月)
- 方案 C 比方案 A 节省 **72%** ($1,485/月)

## 推荐方案

### 当前推荐：方案 B（Tool-as-Skill）
**理由**：
1. 已经节省 70% token
2. 实现复杂度适中
3. 无需两次请求
4. 维护成本低

### 未来考虑：方案 C（延迟加载）
**条件**：
1. 用户反馈对成本非常敏感
2. 大量对话不使用工具
3. 可以接受轻微延迟
4. 团队有能力维护复杂逻辑

## 混合策略（最优方案）

结合方案 B 和 C 的优点：

```typescript
export function getTools(options: {
  lazyLoading: boolean;
  highFrequencyTools: string[];
}): OpenAITool[] {
  if (options.lazyLoading) {
    // 只包含高频工具
    return options.highFrequencyTools.map(name => getToolDefinition(name));
  } else {
    // 使用 Tool-as-Skill
    return [buildUseSkillTool()];
  }
}
```

**工作流程**：
1. 第一次请求：携带 2-3 个高频工具（如 searchBlocksByText）
2. 系统提示词：列出所有可用工具的文本描述
3. 如果 AI 想用高频工具：直接调用
4. 如果 AI 想用低频工具：通过 `<tool>` 标记表达意图，发起第二次请求

**优势**：
- 高频工具无延迟（直接可用）
- 低频工具按需加载（节省 token）
- 最佳的 token 消耗和响应速度平衡
